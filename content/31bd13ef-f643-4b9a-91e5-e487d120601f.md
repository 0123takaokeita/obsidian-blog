## 背景

ルールを守るならTransaction実装は UsecaseでGormのTransactionとか直接呼び出してはいけない。依存関係のルールを守れなくなるから。

WithTransaction() のような関数を実装して対応するプロジェクトを担当したことがあるが、それでも良いのだろうか？
しらべてみるとUnitOfWokrパターンというのがあるらしい。クロージャを使うのでとっつきにくそうだが、確かに綺麗に収まりそうに見える。実際に書き心地を検証してみたい。



## memo

DDD関連のデザインパターンをちょっとづつ勉強していきたいと思う。
別にOOPをするならどれもしってて損はないこと出し、それで実装できると気持ちいい。
「変更に強いアーキテクチャ」の実践としてあらためて勉強したい。

## **1️⃣ ドメイン層関連**

| **パターン**           | **説明**                                             |
| ------------------ | -------------------------------------------------- |
| **Entity**         | 識別子を持つオブジェクト。ライフサイクルを持つ（例：User, Order）。            |
| **Value Object**   | 同一性ではなく値で等価を判断するオブジェクト（例：Email, Money）。            |
| **Aggregate**      | 関連するエンティティ/値オブジェクトをまとめた「一貫性の境界」（例：OrderAggregate）。 |
| **Repository**     | Aggregate を永続化するインターフェース。DBアクセスを隠蔽。                |
| **Domain Service** | 単一のエンティティに責任を持たせられないビジネスロジックを表現。                   |
| **Factory**        | 複雑なオブジェクト生成をカプセル化（例：OrderFactory）。                 |

---

## **2️⃣ アプリケーション層関連**

| **パターン**                           | **説明**                                             |
| ---------------------------------- | -------------------------------------------------- |
| **Use Case / Application Service** | ユースケース単位の処理をまとめる。トランザクションや Repository の呼び出しもここで行う。 |
| **DTO (Data Transfer Object)**     | 入出力データの表現。ドメインモデルと外部 API / UI の間でデータをやり取りする。       |
| **Unit of Work**                   | 複数 Repository の操作を 1 トランザクションとしてまとめる。              |

---

## **3️⃣ インフラ層・共通**

| **パターン**                                   | **説明**                                    |
| ------------------------------------------ | ----------------------------------------- |
| **Adapter / Gateway**                      | DB、外部 API、メッセージキューなどの外部依存を抽象化。            |
| **Repository Implementation**              | Repository の具体的実装（GORM, SQL, MongoDB など）。 |
| **Service Locator / Dependency Injection** | 依存関係の解決やテスト容易性を向上させる。                     |
| **Observer / Event / Domain Event**        | ドメイン内の状態変化を他コンポーネントに通知する。                 |

---

## **4️⃣ 補助的パターン**

| **パターン**                      | **説明**                         |
| ----------------------------- | ------------------------------ |
| **Specification**             | 条件やクエリのロジックをオブジェクト化し、再利用可能にする。 |
| **Policy / Strategy**         | ビジネスルールの切り替えを容易にするパターン。        |
| **Decorator**                 | ドメインオブジェクトに追加責任を動的に付与する場合に使用。  |
| **Command / Command Handler** | コマンド駆動型でユースケースを表現するときに使う。      |

---

### **🔑 ポイント**

- **Entity, Value Object, Aggregate, Repository** は DDD の「必須パターン」
- **Domain Service, Factory, Specification** は必要に応じて使う
- **Unit of Work, DTO, Adapter, DI** は DDD をきれいに実装するための補助パターン
