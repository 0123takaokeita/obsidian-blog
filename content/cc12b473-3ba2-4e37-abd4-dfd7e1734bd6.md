Cursor のエージェントは、Rules や Skills・Commands で挙動をカスタマイズできる。これらのうち**プロジェクトに依存しない汎用的なもの**は、個人の設定として dotfiles で管理し、シンボリックリンクで「持ち歩く」ようにしている。考え方と作業手順をまとめる。

**注意**: ユーザー設定（グローバル）として**ファイルで反映される**のは **Skills** と **Commands** のみ。**Rules** は `~/.cursor/rules` に置いても Cursor は読み込まない。Rules が効くのはプロジェクト内の `.cursor/rules/` だけ。汎用の「ルール」を持ち歩きたい場合は、Skills に同じ指示を持たせるか、各プロジェクトの `.cursor/rules/` に dotfiles の rules をリンクして使う。

## なぜ「汎用」と「プロジェクト固有」を分けるか

Cursor では **Rules** が静的コンテキスト、**Skills / Commands** が動的なワークフローを担う。どちらも `.cursor/` 配下に置く前提で説明されることが多いが、**ユーザー設定でファイルとして有効なのは Skills と Commands だけ**（前述）。次の理由で、汎用設定は dotfiles に寄せたくなった。

- 複数プロジェクトで同じルール・コマンド（コードスタイルや `/pr` など）を使い回したい
- 個人のクセや好みはリポジトリにコミットしたくない
- すでに nvim や tmux などを dotfiles で管理しているので、Cursor も同じように環境ごとに再現したい

そこで、**汎用的なものは dotfiles に置き、プロジェクト固有のものだけ各リポジトリの `.cursor/` に置く**ようにしている。

## 何を「個人設定」にするか・何を「プロジェクト」に残すか

判断の目安はひとつ：「そのリポジトリを抜けても通用するか」で分ける。

**個人設定（dotfiles で管理）の例**

- **Skills**: どのプロジェクトでも使う設計の考え方（デザインパターン、Laravel ならこう書く、など）を SKILL.md で持たせる。Rules と同等の指示を Skill に書けば、ユーザー設定でも効く。
- **Commands**: `/pr`（PR 作成）、`/review`（Linter 要約）、`/update-deps` など。`~/.cursor/commands/` に .md を置くと全プロジェクトで使える。
- 個人のワークフロー（PR の粒度の決め方、ブランチ戦略、コミットの切り方など）も Skill や Command にまとめられる。

**プロジェクト固有（リポジトリの `.cursor/` に置く）の例**

- そのプロジェクトのビルド・テストコマンド、ディレクトリ構成
- **Rules**: ファイルとして有効なのはプロジェクトの `.cursor/rules/` のみ。ここに .mdc を置くか、dotfiles の rules をリンクする。
- 既存パターンへの参照（例: `components/Button.tsx` を参照）

ルールは本質に絞り、長いスタイルガイドをそのままコピーするより、必要なら「〇〇を参照」と書く程度にしておく方が、Cursor の公式ベストプラクティスとも合う。

## dotfiles とシンボリックリンクでの管理イメージ

自分の dotfiles は `~/dotfiles` にあり、その中に `nvim/` や `git/` などアプリごとのディレクトリを置いている。Cursor 用に `cursor/` を追加し、その中に `commands` と `skills`（および参照用の `rules` や規約 .md）を配置した。

**ユーザー設定で反映される**のは `~/.cursor/commands/` と `~/.cursor/skills/` だけなので、この2つを dotfiles にリンクする。`~/.cursor/rules` にリンクしても Cursor は読み込まないため、リンクしない。

```bash
# ユーザー設定として有効なのは commands と skills のみ
mkdir -p ~/.cursor/skills
ln -sf ~/dotfiles/cursor/commands ~/.cursor/commands
ln -sf ~/dotfiles/cursor/skills ~/.cursor/skills
```

Rules を「持ち歩く」場合は、**各プロジェクト**の `.cursor/rules/` に dotfiles の `cursor/rules/` 内のファイルをリンクする（例: `ln -sf ~/dotfiles/cursor/rules/laravel.mdc .cursor/rules/`）。規約ドキュメント（.md）は commands や skills の指示文から「〇〇を参照」と書いて参照するので、dotfiles の `cursor/` 配下に置いておけばよい。

（Cursor のバージョンや OS によって設定の置き場所は変わる可能性があるので、実際のパスは環境に合わせて読み替えてほしい。）

## 作業手順（セットアップ・追加の流れ）

**初回セットアップ**

1. dotfiles を clone し、`~/dotfiles/cursor/` に `commands` / `skills`（および `rules` や規約 .md）を用意する
2. 既存の `~/.cursor/` 配下をバックアップするか、空であればそのまま
3. `ln -sf ~/dotfiles/cursor/commands ~/.cursor/commands` と、各スキルを `~/.cursor/skills/<name>` にリンクする。**Rules は `~/.cursor/rules` にリンクしない**（反映されないため）

**汎用の Skill や Command を追加するとき**

「同じミスをエージェントが繰り返している」と気づいたら、その内容を Skill や Command にまとめる。追加する内容がプロジェクトをまたいで通用するなら `~/dotfiles/cursor/commands/` や `~/dotfiles/cursor/skills/<name>/` にファイルを追加し、スキルなら `ln -sf` で `~/.cursor/skills/` にリンクする。Rules として持ち歩く場合は `~/dotfiles/cursor/rules/` に .mdc を置き、**使いたいプロジェクトの `.cursor/rules/` にだけ**リンクする。

**新規プロジェクトでは**

そのリポジトリ専用のルールだけ `.cursor/rules/` に置く。汎用ルールを効かせたい場合は、dotfiles の `cursor/rules/` をこのプロジェクトの `.cursor/rules/` にリンクする。Commands と Skills はユーザー設定で既に有効なので、プロジェクト側では「このプロジェクト固有の指示」だけを足せばよい。

## 考え方・運用のコツ

> **まずは少なく始める**
> 汎用の Skill や Command を一気に増やしすぎず、繰り返し発生する問題から 1 つずつ追加する。自分たちのパターンが見えてから整理するとよい。

> **中身は「参照」で済ませる**
> 長いスタイルガイドをコピペせず、dotfiles 内のファイルパスや「〇〇を参照」と書いてコンテキストを渡す。コードが変わってもルールが古びにくい。

> **検証可能な目標と組み合わせる**
> 型チェック・Linter・テストがあると、エージェントにも「正しさ」の基準を渡しやすい。個人ルールと組み合わせると、どのプロジェクトでも同じように効く。

## まとめ

プロジェクトに依存しない Cursor の設定を dotfiles に寄せると、環境間の一貫性とプロジェクト間の使い回しがしやすくなる。**ユーザー設定でファイルとして有効なのは Skills と Commands のみ**なので、`~/.cursor/commands` と `~/.cursor/skills` を dotfiles の `cursor/` にリンクする。Rules は `~/.cursor/rules` では反映されないため、汎用ルールは Skill に同じ指示を持たせるか、使いたいプロジェクトの `.cursor/rules/` にだけ dotfiles の rules をリンクする。既に dotfiles でアプリ設定を管理しているなら、`cursor/` を一つ増やすだけで「持ち歩く」設定として扱える。
