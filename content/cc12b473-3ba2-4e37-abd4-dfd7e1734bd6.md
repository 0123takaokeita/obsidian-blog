Cursor のエージェントは、Rules や Skills・Commands で挙動をカスタマイズできる。これらのうち**プロジェクトに依存しない汎用的なもの**は、個人の設定として dotfiles で管理し、シンボリックリンクで「持ち歩く」ようにしている。考え方と作業手順をまとめる。

## なぜ「汎用」と「プロジェクト固有」を分けるか

Cursor では **Rules** が常に参照される静的コンテキスト、**Skills / Commands** が必要時に読み込まれる動的なワークフローを担う。どちらも `.cursor/` 配下に置く前提で説明されることが多いが、次の理由で分けたくなった。

- 複数プロジェクトで同じルール・コマンド（コードスタイルや `/pr` など）を使い回したい
- 個人のクセや好みはリポジトリにコミットしたくない
- すでに nvim や tmux などを dotfiles で管理しているので、Cursor も同じように環境ごとに再現したい

そこで、**汎用的なものは dotfiles に置き、プロジェクト固有のものだけ各リポジトリの `.cursor/` に置く**ようにしている。

## 何を「個人設定」にするか・何を「プロジェクト」に残すか

判断の目安はひとつ：「そのリポジトリを抜けても通用するか」で分ける。

**個人設定（dotfiles で管理）の例**

- どのプロジェクトでも使う設計の考え方（デザインパターン、DDD の区切り方、Laravel ならこう書く、など）
- 汎用コマンド: `/pr`（PR 作成）、`/review`（Linter 要約）、`/update-deps` など
- 個人のワークフロー（PR の粒度の決め方、ブランチ戦略、コミットの切り方など）

**プロジェクト固有（リポジトリの `.cursor/` に置く）の例**

- そのプロジェクトのビルド・テストコマンド、ディレクトリ構成
- 既存パターンへの参照（例: `components/Button.tsx` を参照）

ルールは本質に絞り、長いスタイルガイドをそのままコピーするより、必要なら「〇〇を参照」と書く程度にしておく方が、Cursor の公式ベストプラクティスとも合う。

## dotfiles とシンボリックリンクでの管理イメージ

自分の dotfiles は `~/dotfiles` にあり、その中に `nvim/` や `git/` などアプリごとのディレクトリを置いている。Cursor 用に `cursor/` を追加し、その中に `rules` や `commands` を配置した。

Cursor が参照するパス（例: グローバル設定の `~/.cursor/` や、利用する側のパス）に**シンボリックリンクを張り、実体を dotfiles 側に置く**形にすると、clone するだけで同じ設定をどこでも使える。

```bash
# 例: グローバルな Cursor 設定ディレクトリが ~/.cursor の場合
mkdir -p ~/dotfiles/cursor/{rules,commands}
ln -s ~/dotfiles/cursor/rules ~/.cursor/rules
ln -s ~/dotfiles/cursor/commands ~/.cursor/commands
```

（Cursor のバージョンや OS によって設定の置き場所は変わる可能性があるので、実際のパスは環境に合わせて読み替えてほしい。）

## 作業手順（セットアップ・追加の流れ）

**初回セットアップ**

1. dotfiles を clone し、`~/dotfiles/cursor/` に `rules` / `commands` 用のディレクトリを用意する
2. 既存の `~/.cursor/` 配下をバックアップするか、空であればそのまま
3. 上記のように `ln -s` で dotfiles 内のディレクトリを Cursor が参照するパスにリンクする

**汎用ルール・コマンドを追加するとき**

Cursor のブログでも「同じミスをエージェントが繰り返していると気づいたときにだけルールを追加する」とある。そのタイミングで、追加する内容がプロジェクトをまたいで通用するなら `~/dotfiles/cursor/rules/` や `~/dotfiles/cursor/commands/` にファイルを追加する。実体は dotfiles 側にあるので、リンクを張ってあればどのマシンでも同じ設定が効く。

**新規プロジェクトでは**

そのリポジトリ専用のルールだけ、従来どおり `.cursor/rules/` に置く。個人用の汎用ルールはシンボリックリンクで参照している前提なので、プロジェクト側には「このプロジェクト固有の指示」だけを書けばよい。

## 考え方・運用のコツ

> **まずは少なく始める**
> 汎用ルールを一気に書きすぎず、繰り返し発生する問題から 1 つずつ追加する。自分たちのパターンが見えてから整理するとよい。

> **中身は「参照」で済ませる**
> 長いスタイルガイドをコピペせず、dotfiles 内のファイルパスや「〇〇を参照」と書いてコンテキストを渡す。コードが変わってもルールが古びにくい。

> **検証可能な目標と組み合わせる**
> 型チェック・Linter・テストがあると、エージェントにも「正しさ」の基準を渡しやすい。個人ルールと組み合わせると、どのプロジェクトでも同じように効く。

## まとめ

プロジェクトに依存しない Cursor の設定を dotfiles に寄せてシンボリックリンクで参照するようにすると、環境間の一貫性とプロジェクト間の使い回しがしやすくなる。既に dotfiles でアプリ設定を管理しているなら、`cursor/` を一つ増やすだけで「持ち歩く」設定として扱える。
