Cursor のメインエージェントは、複雑なタスクを **Subagent**（サブエージェント）に委譲できる。委譲時に「どの役割に」「どんな指示を渡すか」を定義しておくと、設計・実装・テスト・レビューなどを役割ごとに任せやすくなる。ここでは、**委譲用エージェント（Subagent）の追加のしかた**と、`cursor/agents/` の運用をまとめる。

**前提**: 委譲は `mcp_task` で行う。メインエージェントが「設計して」「テスト書いて」などの依頼を受けたときに、対応する役割の .md を読み、`prompt` と `subagent_type` を組み立てて委譲する。**Cursor が参照するのはプロジェクトの `.cursor/agents/` 直下の .md のみ**なので、役割ごとに 1 ファイルを直下に置く。

## なぜ Subagent を定義するか

- **役割を分ける**: 設計・実装・テスト・レビューなど、やることが違うので指示のテンプレートと参照先を分けておくと、委譲時の指示がぶれにくい。
- **再利用する**: 同じ役割（例: 実装・批判的レビュー）をどのプロジェクトでも使いたい場合、`cursor/agents/` を dotfiles で管理し、各プロジェクトの `.cursor/agents/` にリンクすればよい。
- **委譲の一貫性**: 「いつ設計に任せ、いつ実装に任せるか」を `when_to_use` で書いておくと、メインエージェントが委譲判断しやすくなる。

## cursor/agents/ の構成

役割 1 つにつき **直下に 1 つの .md** を置く。ファイル名がそのまま役割名（サブエージェントの識別子）になる。

```
cursor/agents/
├── README.md           # 役割一覧と subagent_type の推奨
├── design.md           # 設計
├── implement.md        # 実装
├── test.md             # テスト
├── critical-review.md  # 批判的レビュー
├── conservative-review.md  # 保守的レビュー
└── refactor.md         # リファクタ
```

dotfiles で持ち歩く場合は、`cursor/` に `agents/` を含め、各プロジェクトの `.cursor/agents/` に dotfiles の `cursor/agents/` をリンクする（例: `ln -sf ~/dotfiles/cursor/agents .cursor/agents`）。プロジェクト固有の役割だけ追加したい場合は、プロジェクトの `.cursor/agents/` に直接 .md を追加するか、dotfiles 側の agents をリンクしたうえで、そのプロジェクトだけ別の .md を足す。

## 新しい Subagent を追加する手順

1. **`.cursor/agents/` 直下に `{役割名}.md` を作る**  
   例: `security-review.md`（セキュリティ観点のレビュー用）。

2. **次のセクションを書く**

   | セクション | 内容 |
   |-----------|------|
   | **description** | このエージェントの役割を 1〜2 文で。何を任せるかを明確に。 |
   | **when_to_use** | メインエージェントが委譲すべき状況の目安。ユーザーの言い回しやタスクの種類を書いておくとよい。 |
   | **subagent_type** | `generalPurpose` / `explore` / `shell` のいずれか。設計・実装・レビュー・リファクタは `generalPurpose`、コードベースの広い探索は `explore`、テスト実行・Lint 実行などは `shell` が向く。 |
   | **prompt_template** | 委譲時に渡す指示のテンプレート。`{{user_request}}` や `{{context}}` などのプレースホルダを入れておき、メインエージェントが差し替える。 |
   | **references** | 参照すべき `tools/` や `docs/` のパス。規約は「まずプロジェクトの docs/、なければ ~/.cursor/docs/」で読むと書いておくとよい。 |

3. **README.md の役割一覧に追加する**  
   `cursor/agents/README.md` の表に、ファイル名・役割・想定する subagent_type・要点を 1 行で追記する。後から「どの役割がいるか」を把握しやすくなる。

## ファイル例（最小）

```markdown
---
role: security-review
name_ja: セキュリティレビュー
---

# セキュリティレビューエージェント

## description

コードと設計をセキュリティの観点でレビューする。脆弱性の可能性・認可・入力検証・機密情報の扱いなどを指摘する。

## when_to_use

- ユーザーが「セキュリティ的に見て」「脆弱性がないか確認して」と依頼したとき
- 認証・認可・API の変更をしたあとにチェックしてほしいとき

## subagent_type

`generalPurpose`

## prompt_template

以下の依頼について、セキュリティの観点でレビューしてください。

【依頼内容】
{{user_request}}

【コンテキスト】
{{context}}

- 認可・認証の抜け漏れ
- 入力検証・エスケープ
- 機密情報の露出リスク
- 既知の脆弱なパターンの有無

指摘は具体的に。修正案があれば簡潔に。

## references

- プロジェクトの `docs/` または `~/.cursor/docs/`（セキュリティ規約があれば）
```

メインエージェントは、ユーザーが「セキュリティレビューして」と言ったときにこのファイルを読み、`mcp_task` の `prompt` に `prompt_template` の内容（プレースホルダを置換したもの）と `subagent_type` を渡して委譲する。

## 運用のコツ

- **役割は少なめから**: 最初は design / implement / test / review などよく使うものだけ用意し、パターンが固まってから増やす。
- **prompt_template は具体的に**: 「〇〇の観点で」「出力は簡潔に」など、委譲先に求める振る舞いを書いておくと、返ってくる結果が揃いやすい。
- **references で規約を渡す**: 規約は長く書かず「プロジェクトの docs/ の ○○ を参照し、なければ ~/.cursor/docs/○○」と書けば、Subagent が規約を読んだうえで動ける。

## まとめ

Subagent を追加するには、**`.cursor/agents/` 直下に `{役割名}.md` を 1 つ作り**、`description`・`when_to_use`・`subagent_type`・`prompt_template`・`references` を書く。メインエージェントはこの .md を読んで `mcp_task` で委譲する。`cursor/agents/` を dotfiles に含めてリンクすれば、どのプロジェクトでも同じ役割セットを使い回せる。
