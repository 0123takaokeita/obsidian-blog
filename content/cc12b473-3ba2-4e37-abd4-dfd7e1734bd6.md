Cursor のエージェントは、Rules や Skills・Commands で挙動をカスタマイズできる。これらのうち**プロジェクトに依存しない汎用的なもの**は、個人の設定として dotfiles で管理し、シンボリックリンクで「持ち歩く」ようにしている。考え方と作業手順をまとめる。

**注意**: ユーザー設定（グローバル）として**ファイルで反映される**のは **Skills** と **Commands** のみ。**Rules** は `~/.cursor/rules` に置いても Cursor は読み込まない。Rules が効くのはプロジェクト内の `.cursor/rules/` だけ。汎用の「ルール」を持ち歩きたい場合は、Skills に同じ指示を持たせるか、各プロジェクトの `.cursor/rules/` に dotfiles の rules をリンクして使う。規約ドキュメント（スタイルガイドや development-principles など）は **`docs/`** にまとめ、ルール・コマンド・スキルから「まずプロジェクトの `docs/`、なければ `~/.cursor/docs/`」という**参照順**で読むようにしておくと、プロジェクト固有の規約を優先しつつ dotfiles をフォールバックにできる。

## なぜ「汎用」と「プロジェクト固有」を分けるか

Cursor では **Rules** が静的コンテキスト、**Skills / Commands** が動的なワークフローを担う。どちらも `.cursor/` 配下に置く前提で説明されることが多いが、**ユーザー設定でファイルとして有効なのは Skills と Commands だけ**（前述）。次の理由で、汎用設定は dotfiles に寄せたくなった。

- 複数プロジェクトで同じルール・コマンド（コードスタイルや `/pr` など）を使い回したい
- 個人のクセや好みはリポジトリにコミットしたくない
- すでに nvim や tmux などを dotfiles で管理しているので、Cursor も同じように環境ごとに再現したい

そこで、**汎用的なものは dotfiles に置き、プロジェクト固有のものだけ各リポジトリの `.cursor/` に置く**ようにしている。

## 何を「個人設定」にするか・何を「プロジェクト」に残すか

判断の目安はひとつ：「そのリポジトリを抜けても通用するか」で分ける。

**個人設定（dotfiles で管理）の例**

- **docs/**: 規約ドキュメントの正の情報源。`development-principles.md` や `laravel-standards.md` などを置く。`~/.cursor/docs/` にリンクすると、プロジェクト側に `docs/` がないときにフォールバックとして参照される。
- **Skills**: どのプロジェクトでも使う設計の考え方（デザインパターン、Laravel ならこう書く、など）を SKILL.md で持たせる。Rules と同等の指示を Skill に書けば、ユーザー設定でも効く。
- **Commands**: `/pr`（PR 作成）、`/review`（Linter 要約）、`/update-deps` など。`~/.cursor/commands/` に .md を置くと全プロジェクトで使える。
- 個人のワークフロー（PR の粒度の決め方、ブランチ戦略、コミットの切り方など）も Skill や Command にまとめられる。

**プロジェクト固有（リポジトリに置く）の例**

- そのプロジェクトのビルド・テストコマンド、ディレクトリ構成
- **Rules**: ファイルとして有効なのはプロジェクトの `.cursor/rules/` のみ。ここに .mdc を置くか、dotfiles の rules をリンクする。
- **docs/**: プロジェクト専用の規約（`laravel-standards.md` の上書きやプロジェクト固有のスタイル）を置く。ルール・コマンド・スキルでは「まずプロジェクトの `docs/` を参照し、なければ `~/.cursor/docs/`」とするので、ここにあればそちらが優先される。
- 既存パターンへの参照（例: `components/Button.tsx` を参照）

ルールは本質に絞り、長いスタイルガイドをそのままコピーするより、**docs/ のファイルを参照する**形にしておく方が、Cursor の公式ベストプラクティスとも合う。参照順（プロジェクト docs → ~/.cursor/docs）を揃えておけば、どの環境でも同じ手順で規約を読める。

## dotfiles とシンボリックリンクでの管理イメージ

自分の dotfiles は `~/dotfiles` にあり、その中に `nvim/` や `git/` などアプリごとのディレクトリを置いている。Cursor 用に `cursor/` を追加し、その中に **`docs/`**（規約ドキュメント）、`commands`、`skills`、および参照用の `rules` を配置した。

```
cursor/
├── docs/       # 規約の正の情報源（development-principles.md, *-standards.md 等）
├── rules/      # プロジェクトでリンクして使う .mdc
├── commands/
└── skills/
```

**ユーザー設定で反映される**のは `~/.cursor/commands/` と `~/.cursor/skills/` だけなので、この2つを dotfiles にリンクする。`~/.cursor/rules` にリンクしても Cursor は読み込まないため、リンクしない。**規約ドキュメント**は `~/.cursor/docs/` にリンクしておくと、ルール・コマンド・スキルから「プロジェクトに `docs/` がなければ `~/.cursor/docs/` を参照する」というフォールバックとして使える。

```bash
# ユーザー設定として有効なのは commands と skills。docs はフォールバック用
mkdir -p ~/.cursor/skills
ln -sf ~/dotfiles/cursor/commands ~/.cursor/commands
ln -sf ~/dotfiles/cursor/skills ~/.cursor/skills
ln -sf ~/dotfiles/cursor/docs ~/.cursor/docs   # 規約ドキュメント（フォールバック用）
```

Rules を「持ち歩く」場合は、**各プロジェクト**の `.cursor/rules/` に dotfiles の `cursor/rules/` 内のファイルをリンクする（例: `ln -sf ~/dotfiles/cursor/rules/laravel.mdc .cursor/rules/`）。ルールやコマンドの指示文には「まずプロジェクトの `docs/` の ○○ を参照し、なければ `~/.cursor/docs/○○` を参照する」と書いておけば、プロジェクト固有の規約を優先しつつ dotfiles の規約を補完できる。

（Cursor のバージョンや OS によって設定の置き場所は変わる可能性があるので、実際のパスは環境に合わせて読み替えてほしい。）

## 作業手順（セットアップ・追加の流れ）

**初回セットアップ**

1. dotfiles を clone し、`~/dotfiles/cursor/` に `docs/`（規約 .md）、`commands`、`skills`、必要なら `rules` を用意する
2. 既存の `~/.cursor/` 配下をバックアップするか、空であればそのまま
3. `ln -sf ~/dotfiles/cursor/commands ~/.cursor/commands`、`ln -sf ~/dotfiles/cursor/skills ~/.cursor/skills`、`ln -sf ~/dotfiles/cursor/docs ~/.cursor/docs` でリンクする。**Rules は `~/.cursor/rules` にリンクしない**（反映されないため）

**汎用の Skill や Command を追加するとき**

「同じミスをエージェントが繰り返している」と気づいたら、その内容を Skill や Command にまとめる。追加する内容がプロジェクトをまたいで通用するなら `~/dotfiles/cursor/commands/` や `~/dotfiles/cursor/skills/<name>/` にファイルを追加し、スキルなら `ln -sf` で `~/.cursor/skills/` にリンクする。規約を足したい場合は `~/dotfiles/cursor/docs/` に .md を追加する。Rules として持ち歩く場合は `~/dotfiles/cursor/rules/` に .mdc を置き、**使いたいプロジェクトの `.cursor/rules/` にだけ**リンクする。

**新規プロジェクトでは**

そのリポジトリ専用のルールだけ `.cursor/rules/` に置く。プロジェクト固有の規約があれば `docs/` に置くと、ルール・コマンドの「まずプロジェクトの docs/ を参照」の対象になる。汎用ルールを効かせたい場合は、dotfiles の `cursor/rules/` をこのプロジェクトの `.cursor/rules/` にリンクする。Commands と Skills はユーザー設定で既に有効なので、プロジェクト側では「このプロジェクト固有の指示」だけを足せばよい。

## 考え方・運用のコツ

> **まずは少なく始める**
> 汎用の Skill や Command を一気に増やしすぎず、繰り返し発生する問題から 1 つずつ追加する。自分たちのパターンが見えてから整理するとよい。

> **中身は「参照」で済ませる**
> 長いスタイルガイドをルールやコマンドに貼り付けず、**docs/ のファイルを参照する**形にする。ルール・コマンド・スキルには「まずプロジェクトの `docs/` の ○○ を参照し、なければ `~/.cursor/docs/○○`」と書いておけば、プロジェクト固有の規約を優先しつつ dotfiles をフォールバックにできる。コードが変わっても規約ファイルだけ直せばよい。

> **検証可能な目標と組み合わせる**
> 型チェック・Linter・テストがあると、エージェントにも「正しさ」の基準を渡しやすい。個人ルールと組み合わせると、どのプロジェクトでも同じように効く。

## まとめ

プロジェクトに依存しない Cursor の設定を dotfiles に寄せると、環境間の一貫性とプロジェクト間の使い回しがしやすくなる。**ユーザー設定でファイルとして有効なのは Skills と Commands のみ**なので、`~/.cursor/commands` と `~/.cursor/skills` を dotfiles の `cursor/` にリンクする。規約ドキュメントは **`cursor/docs/`** にまとめ、`~/.cursor/docs` にもリンクしておくと、ルール・コマンドから「まずプロジェクトの `docs/`、なければ `~/.cursor/docs/`」という**参照順**で読めるフォールバックになる。Rules は `~/.cursor/rules` では反映されないため、汎用ルールは Skill に同じ指示を持たせるか、使いたいプロジェクトの `.cursor/rules/` にだけ dotfiles の rules をリンクする。既に dotfiles でアプリ設定を管理しているなら、`cursor/` に `docs/` を足してリンクするだけで「持ち歩く」規約と参照の仕組みが揃う。
